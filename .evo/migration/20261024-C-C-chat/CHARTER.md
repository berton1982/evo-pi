## 3. 不做清单

1. **扩展 UI 宿主**（`ChatWindow` 里渲染 extension UI 请求的那部分）——它依赖 `useAgentSession` 的 extension protocol，属 C-A 后续，本次不迁。
2. **会话归档 / 多会话切换 / URL 同步**——属 C-B 会话编排，本次只在"当前会话"上工作。
3. **代码块语法高亮与 Markdown 渲染库替换**——沿用现有依赖，不引新的渲染管线。
4. **骨架屏与虚拟滚动**——消息量大时的性能优化不在本次验收范围（记录为已知风险）。

## 4. 验收门

- L1 域函数（消息分组/折叠/参数格式化的纯函数）单测
- L2 用例（发消息/改模型/改推理级别/压缩上下文）用假端口
- L3 组件（消息列表三态、工具条按钮禁用逻辑）
- L4 端到端：`e2e/chat/*` 打到 `30041`，壳的 12 条 `blocked` 行转 `done`
- L5 双开对账：同一夹具在 `30141` / `30041` 各拍一次保真快照，逐条登记差异
- L6 人工验收（用户签字，不可代签）

## 5. 已知风险

1. **输入工具条的 12 个控件共享同一份 agent 状态**，切错边界就会把"容器"变成第二个 god（`ChatWindow` 2282 行正是这么长出来的）——必须按 schema 拆成 presenter + 各自位置。
2. **消息渲染的两套路径**（流式增量 vs 完整消息）容易只迁一套，另一套在真实会话里才暴露；C6 必须用真会话回放。
3. **`ChatWindow` 与 `useAgentSession` 耦合**：后者已由 C-A 迁（停在 C4，未实现），本次必须走端口/回调，不能直接 import pi-web 的 hook。
4. **重量级渲染**（2161 行的 `MessageView`）里混着工具调用展示逻辑，容易出现"渲染对了但工具语义错了"。
