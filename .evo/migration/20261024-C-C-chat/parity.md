### 采集现状（源码级，2026-10-24 更新）

`cwd` 与 `session` 互斥（`lib/initial-navigation.ts:14`）、会话恢复靠 sessionStorage 的 `pi-web:tab-open-session`（`lib/tab-session.ts:22` + `AppShell.tsx:637`）、恢复动作在侧栏（`SessionSidebar.tsx:1140-1155`）——三点已确认并写进 `harness/fidelity.mjs` 的 `open()`。

**共享夹具目录已落地**（`harness/start-parity.sh`）：两侧进程都以 `PI_CODING_AGENT_DIR=/tmp/parity-agent` 启动，夹具会话由脚本复制进去，**evo-pi 不再读写用户 `~/.pi/agent`**。实测两侧 `/api/sessions?cwd=…` 返回同一条会话，evo 侧页面渲染出 61 个 `[data-testid=chat-markdown]`。

**仍未闭环的最后一环：采集窗口不对称**。pi-web 只渲染尾部（懒加载），evo-pi 从头渲染；而快照抓的是前 N 条可及元素，于是"左边是最后一条、右边是第一条"。
解法（下一步）：两侧都先 `scrollTo` 到同一位置（顶部/底部）再采，或对同一条消息取窗口——不是数据问题，也不是打不开。

## 采集窗口对齐（已解决，2026-10-24）

**问题**：会话面两侧渲染窗口宽度不同（pi-web 懒加载 N 条、evo-pi 全量渲染），按 DOM 序号截尾部永远错位——实测 18/18、24/24 都是 0% 覆盖率。

**解法（已实现）**：`harness/fidelity.mjs` 新增 `captureBlocks()` + `alignBlocks()`：
1. 每条消息算一个**归一化文本哈希**（FNV-1a）并采该消息内的语义锚点；
2. 两侧从尾部找**最长共同后缀**（最多 30 条）；
3. 只比这段对齐区间内的锚点集合。

**实测**：
```
[chat] 已按消息内容对齐：共同后缀 4 条消息（pi 起点 0，evo 起点 2）
[chat] 可及元素：pi-web 112 / evo-pi 112
覆盖率：100.0%    只有 pi-web 有：0
```

**这个 100% 的含义要写清**：锚点名称由元素文本派生，按文本哈希对齐后文本当然一致，所以它证明的是
**"同一批消息两侧渲染出的语义结构集合相同"**（同样的标题/表格/列表/代码块数量与层级），
**不证明样式一致**（字号、间距、颜色由 `.markdown-body` 的 CSS 决定，属于 T-21 的读数判据）。
角色分布实测：pi `{code 68, td 28, li 12, h2 8, th 8, table 3}` / evo `{code 92, td 51, li 19, th 15, h2 13, table 6}`——
差值是"窗口外的消息"，不是结构缺失。
